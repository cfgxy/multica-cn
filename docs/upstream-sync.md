## 二、同步机制（交付物 1）

### 2.1 节奏与触发

- **例行窗口**：每周一个同步窗口，单窗口处理上游增量约 80 提交（处于 ferren 已验证的 44–154 单批实践区间内，窗口越小冲突面越小）。
- **事件触发**（不等窗口）：上游 critical 安全修补（C-security 类）对账后即时吸收并单独上报；上游框架大版本（如 Expo SDK 大版本）单列批次。
- **批次单位**：按对账簇吸收，一簇一 PR；簇结论继承交付物 3 四类判定，增量窗口用归档脚本（`cluster.py`/`gen_ledger.py`）自动聚类。

### 2.2 每窗口流程（六步，全程可机械核对）

1. **冻结基线**：窗口开工钉死 upstream/main 与 origin/main 完整 SHA（同本单分派卡纪律）。
2. **增量对账**：跑聚类规则产出增量对账清单（簇主题、四类结论、证据强度、路径级冲突面、涉迁移 stems）。
3. **逐簇吸收**：需要吸收→cherry-pick 改造；冲突需重做→按 fork 体系重做；明确不吸收→放弃理由登记入同步日志；已实现等价→登记 fork 锚点。
4. **迁移防撞闸**：按第三章规则执行，断言不过禁止合入。
5. **验证闸门**：全量 `make check` + 槽位库迁移冒烟 + 被吸收域定向测试。
6. **同步日志**：窗口基线、逐簇结论、重编号映射、冲突裁决写入同步日志（仓库登记文档 + bd memories 双落点）。

### 2.3 冲突处理规则

- 路径级冲突面（重叠文件数）作为吸收顺序与工作量预估信号；内容级冲突逐文件裁决：上游语义优先，fork 自有功能线与治理体系显式保留。
- 已识别的代码级交叠锚点吸收前必须先合并设计，禁止直合：
  - **daemon 终态报告**：上游 MUL-7471 持久重放 vs fork completion reconcile 幂等闸 `4c38daacc952ec4b5a61367495047eb56390e3c5`——同域不同机制，先统一终态语义；
  - **lark 面**：fork 有 RUYI-572/546 自有改造，上游 lark 修复须 fork 侧重放验证；
  - **prompts/skills**：fork 治理体系自有（迁移 908/921/923 + self-evolution 线），上游改写项逐条重做；
  - **mobile 框架升级**：fork 分支重做并回归自有功能线（时间线卡片、派工、决策中心等）。

### 2.4 验证闸门与回滚

- 簇级 PR 独立可 revert，任一簇吸收不绑其他簇；
- 吸收批次经槽位 QA（qa 相位），QA `PASS` 且 Leader 本地核对完成后合并（继承既有协作闸门）；
- 窗口级回退：按簇逆序 revert，同步日志记录回退序列；
- 同步失败不阻塞主线：fork 自有功能线推进与同步窗口解耦。

## 三、迁移防撞专项设计（交付物 2）

### 3.1 号段分工

- **fork 专用 9xx（900–999）**：fork 新迁移一律 9xx，经 `.multica/ALLOCATIONS.md` 登记簿协调（RUYI-609 制度延续）；上游实测 900+ 占用为零。
- **450–899 上游带**：上游在该带持续新增并重编号（空号 507/508/517 为证），宣布为「上游不稳定区」——fork 不在该带新增自有编号；被吸收上游迁移保留原号原 stem；fork 侧迁移（自有或此前吸收）与之撞号时由 fork 让号。

### 3.2 上游迁移吸收规则

1. 吸收前跑 stem 差集核对：上游窗口新增 stems ∩ fork 磁盘 stems = 撞号集（本次实测 {457,458}）。
2. 被吸收上游迁移保留原号、原 stem、原 SQL 内容迁入（保留 down/up 配对），仅做必要适配，diff 最小可审。
3. 撞号时 fork 侧让号：fork 撞号迁移（自有或此前吸收）重编号至 9xx 空闲号，按窗口顺序连续取号，三源核对后经登记簿记 `reserved`。
4. fork 已应用迁移的让号重编，须对每个已应用库执行 `schema_migrations` 记账改写（`UPDATE schema_migrations SET version = '<新 stem>' WHERE version = '<旧 stem>'`，`applied_at` 保留原值；RUYI-212 纪律）——槽位库由持槽角色协调串行执行，本地共享主库与生产主库须 Owner 逐次授权。

### 3.3 机械闸门

吸收 PR 固化三条断言（并入既有防误降守卫与账本门禁，最小扩展）：

- 来源可辨：fork 磁盘 stems 二分——fork 自有与让号重编 stems 全部 ∈ 9xx；被吸收上游 stems 编号 ∈ 上游带且 stem 名与上游逐字一致；450–899 带内禁止出现非上游来源的新增 stem；
- 三源协调：main 磁盘 / 各库 `schema_migrations` / ALLOCATIONS.md 三方无撞号；
- 覆盖完备：被吸收 stem 集合 = 上游窗口 stem 集合，无遗漏。

### 3.4 本单实测 {457, 458} 处置（按 Owner 决策 2：fork 侧让号）

- fork `457_plugin_public_listing`/`458_plugin_package_public_index` 已进生产基线，让号重编至 9xx 空闲号（建议自 945 起，以登记簿实况为准），只改文件名不改内容，并对全部已应用库执行记账改写（生产库须 Owner 逐次授权）；
- 上游 `457_task_message_output_truncated`/`458_agent_task_cancellation_actor` 吸收时保留原号原 stem 迁入，不再重编号。

## 五、备选方案与回退

**备选 A——merge 周期制**：每窗口 `git merge upstream/main`。优点：历史保真、一次消解全部冲突；缺点：冲突集中爆发（本窗口即 608 文件 + 120 stems 迁移面冲突），迁移账本风险集中，单窗失败成本高。不采纳为主方案，保留作「久隔之后追平」的兜底路径。

**备选 B——quilt 补丁栈**（ferren 实践）：fork 自有面作为补丁栈浮于 upstream，同步 = rebase 栈。优点：冲突逐补丁消解、长期最干净；缺点：fork 已领先 1065 提交，补丁栈改造跨全历史，成本远超 3 人日，违背手术式演进。不采纳；若未来 fork 自有面大幅收缩可重评。

**推荐方案**：簇级吸收 + 让号防撞（本方案）。改动面最小、簇级可回退、闸门全部可落在既有基建上。

**回退路径**：簇级 PR 独立 revert；窗口级逆序 revert；机制失当（如单窗成本持续超预算）则退回备选 A 追平；重编号均留 old→new 映射，可逆向追溯。
