## 一、阶段 1（统计 usage 屏）详细产品验收标准

### A. 入口与权限

- A1【QA 实机】工作区成员进入手机端工作区「更多」页，可见并点入统计入口；入口命名与 web 侧 usage 语义一致。失败判据：入口缺失、或命名使成员无法将其与 web usage 对应。
- A2【QA 实机】统计入口可达性与 web usage 页一致：凡 web 端可见 usage 的账号，手机端同账号入口可达；web 端不可见者手机端同配置不可达。失败判据：任一账号双端可见性不一致。

### B. 时间窗口（parity 基座）

- B1【QA 实机】首屏默认窗口为最近 30 天（含今天），KPI、趋势、排行、失败四区基于同一窗口。失败判据：默认窗口非 30 天，或各卡片窗口不一致。
- B2【QA 实机】提供 1d/7d/30d/90d/180d 五档快捷区间；切换后全页数值同窗口刷新。失败判据：档位缺失、或切档后存在卡片仍显示旧窗口数值。
- B3【QA 实机】窗口可向前翻页且步长等于窗口长度（1d 档步进 1 天、30d 档步进 30 天），可一键回到当前；当前位置时不能翻到未来。失败判据：步长错误、可翻至未来日期、或无回当前入口。
- B4【静态验收 + 实机抽查】1d 档语义为「今天」（查看者时区自然日 00:00 起），非「最近 24 小时」；窗口标签显示起止日期。静态判据：窗口计算与 web 复用同一 core 函数；实机抽查：跨时区账号窗口起止与 web 一致。
- B5【QA 实机】项目过滤器支持「全部项目」与单项目；筛选后 KPI、趋势、排行、失败四区联动。失败判据：过滤器缺失或部分卡片不联动。

### C. KPI 与数值 parity（主判据）

- C1【QA 实机】KPI 区含成本、tokens、运行时长、任务数四项，每项标注统计窗口天数。失败判据：缺项或无窗口标注。
- C2【QA 实机·双端对照】同一账号、同一 workspace、同一起止窗口、同一项目过滤下，手机端任一 KPI 数值与 web usage 页对应数值一致，成本数值双端一致（同价目表）。失败判据：任一项数值不一致。取证：双端同窗口截图并排。
- C3【静态验收】四 KPI 与失败率口径与 web 同源（复用同一 core 查询与聚合）。静态判据：查询层复用关系可由 import 锚点复核。

### D. 趋势图与排行榜

- D1【静态验收 + 实机抽查】趋势图支持日/周粒度切换，可用粒度与窗口长度绑定：1d/7d 仅日粒度、30d/90d 日周均可、180d 仅周粒度，与 web 规则一致。失败判据：粒度可用性与 web 不同。
- D2【QA 实机】排行榜提供 tokens/成本/时长/任务数四种排序，切换后行序与进度条同步重排。失败判据：排序维度缺失或行序不随排序变化。
- D3【QA 实机】排行榜数值在双端同窗口同过滤下一致（counts parity）。失败判据：任一排序维度下不一致。

### E. 失败视图（对应 web Errors tab）

- E1【QA 实机】统计屏含失败视图，含每日失败趋势与按 agent 的失败分布两个面。失败判据：任一面缺失。
- E2【QA 实机】失败视图数值与 web 同窗口一致；失败率的分母口径在文案中明示（与 web 措辞同义）。失败判据：数值不一致或分母无明示。
- E3【静态验收 + 实机抽查】失败视图粒度切换规则与 web 一致（30d 及以上窗口提供周粒度）。失败判据：粒度规则不一致。

### F. 状态与边界

- F1【QA 实机】所选窗口无任何使用数据时，KPI 显示 0 值/空态视图，不报错、不永久 loading；空态语义与 web 一致。失败判据：空窗口下出现报错、死 loading 或混入旧窗口数据。
- F2【静态验收 + 实机抽查】刷新语义与 web 一致：进入页面拉取最新、停留期定期自动刷新（web 为约 1 分钟）；统计数据不依赖 WS 推送（web 亦无）。失败判据：手机端引入 web 不存在的实时通道语义，或进入页面不刷新。
- F3【QA 实机】网络异常时展示错误态与重试入口，重试成功后恢复；不出现白屏或新旧数据混排。失败判据：断网后白屏、或恢复后数值与 web 不一致。
- F4【实机抽查】失败视图加载不阻塞使用视图首屏（按视图独立加载态，与 web 一致）。失败判据：失败数据慢时整页阻塞。

### G. 文案与呈现

- G1【静态验收 + 实机抽查】统计页文案与应用语言联动，语义与 web 同源文案一致（同一 locales 包）。失败判据：出现 web 文案包之外的自造文案或语言不联动。
- G2【QA 实机】金额/时长/tokens 的格式（单位、分隔符、日期时区）在抽查样本上与 web 展示一致。失败判据：同类数值双端格式不同导致误读。

### 阶段 2：Runtime 节点管理补全
- R1【QA 实机】全量列表页可见 voice/cli/daemon 三类节点并支持类型筛选；节点总数与 web runtimes 页一致（counts parity）。失败判据：任一类型缺失或总数不一致。
- R2【QA 实机】详情与操作 parity：凭据状态三态（已配/未配/异常）展示、改名、删除/解绑流的确认文案与结果与 web 语义一致；删除/解绑必须二次确认。失败判据：破坏性操作无确认流，或结果与 web 不一致。
- R3【QA 实机·回归】既有语音实例列表、详情、注册流在新信息架构下行为不变；语音实例详情入口在新列表内可达。失败判据：语音流任何一步行为回归。
- R4【QA 实机·负向】无 runtime 管理权限的账号，管理操作在 UI 层不可达（不可触发，而非仅不可见）；权限面与 web 一致。失败判据：低权限账号可触发任一管理动作。
- R5【流程】本阶段动工前吸收 RUYI-640（MeshConsole 调研）结论；若节点管理服务端面扩容，验收标准按扩容面增补后再派发。

### 阶段 3：空间管理核心
- W1【QA 实机】有权限账号（与 web 同权限面）可在手机端完成 workspace 改名并双端生效；无权限账号该操作 UI 层不可达。失败判据：双端结果不一致或权限闸门失效。
- W2【QA 实机】成员管理四动作（列表/邀请/角色变更/移除）与 web 同 mutations 生效一致；被移除成员的手机端会话按 web 语义失效。失败判据：任一动作结果双端不一致。
- W3【QA 实机·高危】workspace 删除仅限有权限账号、二次确认强度与 web 对齐、删除后全部成员端不可达；本条仅在专用测试空间验证。失败判据：确认流弱于 web 或误删非目标空间。
- W4【QA 实机】labels 与 issue-statuses 的增删改排序与 web 一致；变更后 issue 编辑侧选择器即时反映。失败判据：选择器与配置面数据不同步。
- W5【标注·未决即排除】integrations 面验收标准待决策 1 裁决后增补；当前按「不进手机端」书写。

### 阶段 4：自进化一期（overview 只读 + proposal 审批 + retrospective 查看）
- S1【QA 实机】overview 数据与 web self-evolution 同源一致；只读视图不出现任何 owner 闸门操作入口。失败判据：数据不一致或只读页出现可触发写动作。
- S2【QA 实机·负向】owner 账号可在手机端完成提案 diff 查看 → 审批/驳回；非 owner 账号审批动作 UI 层不可达（不可触发，非仅隐藏），权限面与 web 同为 owner-only。失败判据：非 owner 可触发审批。
- S3【QA 实机】手机端审批后，web 端提案状态同步变更（同数据身份、同 WS 事件覆盖）。失败判据：状态双端不一致。
- S4【QA 实机】retrospective 查看：owner 见 run 结果、member 见读面，与 web 权限一致；无权限账号不可达。失败判据：权限面与 web 不一致。
- S5【QA 实机】quiz/quality/versions/knowledge/skill 等非本期 tab 在手机端不出现半成品入口。失败判据：出现不可用或残缺入口。

### 阶段 5：Skills / Autopilots（范围受决策 1 约束）
- K1【QA 实机】Skills 列表/详情/版本/usage 数值与 web 同源一致；恢复（restore）操作权限与 web 一致。失败判据：数值或权限面不一致。
- K2【QA 实机】Autopilots 列表/详情/配额数值与 web 一致。失败判据：数值不一致。
- K3【QA 实机·负向】无对应权限账号的相关入口与操作 UI 层不可达。失败判据：权限闸门失效。
- K4【标注·未决即排除】marketplace/billing/integrations 验收标准待决策 1 裁决后增补；当前按「不进手机端」书写。

### 阶段 6：Admin（范围受决策 2 约束）
- M1【QA 实机】超管账号可在手机端查看 users/workspaces 只读列表与审计记录，数据与 web admin 一致。失败判据：数据不一致。
- M2【QA 实机·负向】非超管账号的 admin 入口与数据在 UI 层完全不可达（不可触发，非仅隐藏）。失败判据：非超管可达任一 admin 面。
- M3【标注·未决即排除】全部写操作（含 impersonate/超管授予/用户禁用）按「留桌面端」书写，手机端不出现写入口；决策 2 裁决开放后按被开放动作增补验收：动作命中与 web 相同 API 与审计落点（admin_audit_log），审计可追溯。

### 每阶段通用验收（引用 Leader 分期方案，适用全部六阶段）
- counts / permissions / state enums / data identity 四项 parity 逐阶段核验。
- WS 事件覆盖与 web 一致（统计屏特例见 F2：web 无 WS 依赖，手机端一致即可）。
- 涉权限屏验证权限闸门在 UI 层不可达（负向断言，非仅隐藏）。
