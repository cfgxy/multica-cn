## 0. 增量总览与范围声明

Owner 七条中，第 1 条（评估体系论证）与第 7 条（数据源可选化）归架构（ADR v2），本增量不涉及；第 2–6 条的产品口径在 §9–§12 定义。增量范围一句话：**给「看得见质量」的自进化装上「行动闭环」**——测验回答「改好没有」，提案池回答「下一步改什么、怎么改」，知识库回答「学到了什么」，skill 回答「怎么把会做的事固化下来」。

【判断】四块共享同一个骨架：**扫描/AI 只产草稿与提案，Owner 打勾才立法，一切产出可追溯版本**。这与 v1 §3.6 定稿的权限模型同构，不新增权力主体。

明确不做（增量范围外）：AI 自动改写并直接切换 prompt（v1 §2.4 已排除，Q7 已按 Owner 意向定稿为「仅到提案」）；知识/skill 的跨 workspace 共享；将成员任务交接回报（STAGE_COMPLETE 等）改为机器生成——扫描承接的是「经验提炼型复盘」，协作交接回报不属复盘，不在取消范围。

## 9. 测验机制（Owner 第 2 条）

Owner 原文（出处评论 2026-09-25 00:06）：「要有测验机制，每次更新Prompt后要让Agent在给定的题库中做一轮测验看看是变好了还是变差了，防止问题回归」。

### 9.1 一道「题」是什么【判断】

一道题 = 一个**金标准任务实例**，不是问答题。被测 agent 在受控环境执行题面任务，评分器按验收条款对产出物机械判分。一道合规的题必须同时包含以下五要素，缺任一不可保存：

1. **题面**：给被测 agent 的任务指令，格式模拟真实 Issue 输入（目标/背景/约束），指令本身不含真实 Issue 号、真实用户数据。
2. **验收条款清单**：≥3 条可机械判定的判据，每条独立可判 PASS/FAIL（例：「产出文件存在且校验值匹配」「评论含完整 SHA」「未写入禁区路径」）。条款即判分依据，不允许「完成度良好」类表述。
3. **证据落点声明**：每条验收条款对应评分器可读取的证据位置（产物文件路径、评论字段、命令输出摘要）。评分器只读声明的证据判定，不自由发挥。
4. **适用映射**：被测智能体角色 + 触发它的 prompt 层级（见 9.3 映射表）。
5. **判分配置**：通过阈值（如 PASS 条数比例 ≥80% 记该题通过）与题型分类，随题版本化。

### 9.2 答案对错由谁判定【判断】

- **机器判定是唯一裁决**：评分器按验收条款 + 证据落点逐条输出 PASS/FAIL，附证据引用；无证据引用的判定无效。题目总分 = PASS 条数 ÷ 总条数。
- **AI 只做归因不做裁决**：FAIL 的题由分析器（LLM）产出失败归因说明（哪一步偏离、疑似什么原因），归因写进测验报告供人阅读，**不改变 PASS/FAIL 结论**。理由：LLM 自由裁量的判分不可复现，会让同一份答卷两次判出不同结果；可复现性是「前后版本可比」的前提。
- 判分配置与题同版本；改判分配置 = 出新题版本，历史成绩不追溯重算。

### 9.3 一次测验覆盖哪些角色与哪级 Prompt【判断】

按「被改的 prompt 层级」定测验范围，不做无差别全量大考。映射关系是平台配置，纳入版本管理：

| 被修订的层级 | 必考题组 | 默认规模上限 |
| --- | --- | --- |
| 智能体提示词 | 该智能体的专属题组 | 5 题 |
| 小队 instructions | 该小队全体成员题组（每成员抽核心题） | 每成员 3 题 |
| 项目 instructions | 绑定该项目的常用角色题组（映射可配） | 每角色 3 题 |
| 空间 context | 全空间各角色核心必考题 | 每角色 1–2 题 |

规模上限是成本护栏（一次测验 = 题组规模 × 每题一个受控 run），Owner 可调，调整留痕。

### 9.4 测验在什么时机跑【判断·修订 v1 §5.3】

- **版本生效后自动必跑**（Owner 定稿口径，取代 v1 的「切换后可选触发」）：任一级 prompt 产生新生效版本 → 系统自动创建一次测验任务，范围按 9.3 映射，测验记录关联新版本号。
- **手动触发**：看板对任意历史版本可手动重考（排查环境噪声、复核争议结果）。
- **周期巡考**：定期对当前生效版本全量重考，防长期漂移——列 P1（开放问题 Q12 不含此项，避免混淆；周期巡考的频率归 ADR v2 工作量权衡）。
- 测验与生效**解耦**：测验不阻塞版本生效本身（生效语义沿用 v1 §3.3「保存即生效」单一生效语义），测验结果是事后质量信号。约束力问题见 9.6。

### 9.5 「变好了还是变差了」的结论口径【判断】

**跟旧版本比，不跟满分比**：

- 基线 = 上一生效版本在同一题组上最近一次的逐题成绩。题库启用时对当时生效版本跑一轮建基线。
- 逐题对比产生「回归题」集合：本次 FAIL 且基线 PASS 的题。
- 版本级结论三档（全机械）：存在回归题 → **「存在回归」**；无回归题且题组均分 ≥ 基线 → **「改善或持平」**；无回归题但均分 < 基线 → **「轻微下滑（无单项回归）」**。
- 版本连续快速变更、上一版测验未完成时：以最新已完成测验为基线并在报告标注「跳版对比」。测验排队不互相阻塞。
- 每次测验成绩记录：被测版本号（四级全记，归因键）、题版本号、逐题判定与证据引用、结论档位。

### 9.6 测验结果是建议还是闸门【判断 → 开放问题 Q10】

【事实】v1 定稿「保存即生效、无草稿态」⇒ 测验必然发生在生效之后 ⇒ 测验对本次生效只能「事后预警」，不可能「事前阻断」。

- 推荐（A）：**建议与标签**——未跑测验的版本带「未测验」标签；结论为「存在回归」的版本带红色「存在回归」标签 + 回归题清单，在版本台账高亮；是否回滚由 Owner 决定。理由：题库会有假阳性（环境噪声、题目自身缺陷），硬闸门等于让题库质量掌握发布权；且机器闸门不得约束 Owner 修法权。
- 备选（B，列 Q10）：空间/小队级等大范围 prompt 变更可配置「测验未完成前对新 run 暂缓生效」——不影响已启动 run，不引入第二生效状态记录，仅在埋点层延迟登记。此选项给 Owner 权衡，非推荐。

### 9.7 题库治理【判断】

- 题库是平台资产，修订走与 prompt 相同的版本管理（整体快照、只追加、copy-forward 回滚）与立法门闸（结构校验、凭据模式检查）。
- 写权限仅 Owner 及授权执行会话；成员可提案新题/改题（经提案池，§10）。
- 题目本身可被测验结果反噬：某题在多个版本上成绩无差异（区分度失效）时，测验报告输出「低区分度题」清单，作为题目修订提案的输入。

## 10. 底座复盘内化与提案池（Owner 第 3 条）

Owner 原文：「之前用Autopilot总复盘+每Issue复盘报告的模式我希望可以内化到底座层支撑，Issue中不要再有显式的复盘了，底座层面上做每日定时任务扫描每个Issue、每个Run甚至Langfuse，来总结Prompt改进草案、项目认知、经验教训、踩坑记录，把提案=>立法的过程显化出来（每天打打勾就能修订Prompt）」。

### 10.1 每日扫描的定位与产出物【判断】

- **扫描器**是自进化模块的内置定时任务（调度载体选型归架构；【事实】平台已有 autopilot 定时/触发载体与 runs 历史，此处仅记录现状不选型）。
- 扫描窗口：**前一自然日（D-1 全天，时区随平台配置显式声明）完结的 Issue 与 run** 及其消息序列；Langfuse 为可选数据源（Owner 第 7 条，接入与否不影响本节产品语义）。失败、返工、违规、重试事件优先提取——它们是教训与踩坑的主要来源。
- 产出 = **提案草稿**，统一进入**提案池**，共五类：①Prompt 修订草案 ②项目认知 ③经验教训 ④踩坑记录 ⑤skill 提案（②–⑤ 定义见 §11、§12）。
- 每条草稿必填：类型、摘要（1–3 句）、建议动作、**证据引用（≥1 条 issue/run 链接，缺失即不发布）**、置信标记（多例证据/单例推断）、扫描批次号、扫描时相关实体 prompt 版本号。
- 扫描批次日志：每日一条（扫描范围、产出数、丢弃数、异常），**零产出日也记录心跳**——扫描任务「跑没跑、扫了什么」永远可查。
- 同一 run 不被两个批次重复提案；批次重跑不产生重复草稿（幂等）。

### 10.2 「Issue 内不再写显式复盘」后，原本的信息去哪【判断】

原复盘模式承载三类信息，去向逐一分清：

| 原承载 | 内容 | 新去向 |
| --- | --- | --- |
| Issue 内显式复盘评论 | 经验提炼、规则/知识改进草案 | 每日扫描自动起草入提案池；**成员主动提交提案的入口保留**（成员不依赖扫描器也可直接提交） |
| bd memories | 踩坑、机制认知、经验教训 | 平台知识库（衔接关系与结论见 §11.5） |
| 任务交接回报（STAGE_COMPLETE、分派卡、验收报告） | 协作交接事实 | **不变，保留在 Issue**——这是协作回报，不是复盘，不在取消范围 |

【判断】本节只定义平台能力与承接关系；现行协作手册中复盘条款的修订属 Owner 立法，作为依赖项标注（§15 Q13 采纳后随 ADR v2 一并提请），本规格不直接改写任何纪律条款。

### 10.3 「每天打打勾就能修订 Prompt」的完整产品语义【判断】

- **勾选对象**：提案池中类型①的「Prompt 修订草案」。一条草案必须已写明：目标实体（哪级哪个）、修订意图（一句话）、修订后的内容草案（全文或明确 diff 指令）。
- **打勾（采纳）之后发生什么**，四步全自动 + 一步人审：
  1. 提案状态 → 「已采纳」；
  2. 系统按草案内容生成目标实体的**新版本草稿**与 diff 预览；
  3. 草稿过**内置立法门闸**（结构锚点、文风、凭据模式——与手工保存同一套）；FAIL → 提案退回「需修订」并附违规明细，不产生版本；
  4. 门闸通过 → 进入 Owner **确认步**：展示 diff + 门闸结果，Owner 点确认；
  5. 确认后按 v1 §3.3 既有语义生成新版本并生效；该版本审计记录**关联来源提案号**（立法结果可反查到是哪条提案、哪次扫描产出）。
- 采纳后是否保留第 4 步确认 → Q11（推荐保留：AI 改写可能有门闸测不出的语义偏差，一步 diff 确认成本极低）。
- 修法权落位：扫描器与 AI 全程只有**提案权**，采纳、确认、生效的写动作全部 Owner（或其授权执行会话）——提案=＞立法的显化不是修法权下放，是修法权拿到一张待办清单。

### 10.4 不勾的提案怎么留存与过期【判断】

- 提案池留存所有草稿；默认 **30 天**未被采纳的提案自动转「已归档」（不删除、可检索、可恢复重提）。
- 同一事实被后续批次再次识别时：与既有未归档同类提案**合并**（追加佐证，不新建）；Owner 可手动合并/拆分，动作留痕。
- 归档时若该提案关联的 prompt 已变更，归档记录标注「建议内容基于版本 vX，现已过时」。

### 10.5 与提案池统一的界面语义【判断】

提案池是「提案=＞立法」过程的显化界面，五类提案共用一套状态机：`草稿 → 已采纳 → 已生效（挂版本号）/ 已转化（知识条目、skill 的转化结果）→ 归档`，旁路状态「需修订」（门闸退回）。每条提案可以看到：谁产出（扫描批次/成员）、证据是什么、立法结果是什么。状态流转全程留痕。

## 11. 知识显化（Owner 第 4 条）

Owner 原文：「基于第三点，可以把 项目认知、经验教训、踩坑记录 这些东西也做显化，便于搜索查询」。

### 11.1 三类条目的形态与必填字段【判断】

三类互斥判据：**描述事实 = 认知；指导行动 = 教训；现象 + 环境 + 解法 = 踩坑**。分类错误的条目人工可改类，改类留痕。

| 类型 | 回答什么 | 必填字段 |
| --- | --- | --- |
| 项目认知 | 这个项目/系统是怎么运转的（机制性事实） | 标题（陈述句）、所属项目、正文、依据（≥1 条 run/issue/代码位置引用）、首次确认时间、状态 |
| 经验教训 | 做这类事什么做法有效/无效 | 标题、适用范围（角色/任务类型/项目，可多选）、正文（含「应当/避免」表述）、依据、状态 |
| 踩坑记录 | 具体环境/依赖/命令的坑与解法 | 标题（现象一句话）、现象、环境（平台/版本/路径等可定位信息）、解法（无解时填「未解决 + 绕行方式」）、依据、状态 |

条目内容必须是可被反证的具体陈述；「可能会」「建议注意」类空泛表述在保存门闸校验中拒绝。

### 11.2 来源与去重【判断】

- 来源三条：①每日扫描自动起草（初始「待确认」状态）；②成员经提案池直接提交；③bd memories 一次性汇入（§11.5）。
- 去重口径（机械）：新条目与同项目同类型的既有「有效」条目判重命中时，**不新建**，转为在既有条目下追加佐证并留痕；人工可推翻合并判定并拆分，拆分动作记录。
- 生命周期三态：`待确认 → 有效 ⇄ 已过时`。被新认知推翻的条目标「已过时」不删除（保留演进史）；「待确认」条目在检索结果中始终带状态标签，不被当作已核实知识。

### 11.3 检索入口支持的查法【判断】

1. 关键词全文检索（标题 + 正文）；
2. 按项目过滤（项目认知必挂项目，其余两类可选挂）；
3. 按类型过滤（三类）；
4. 按状态过滤（待确认/有效/已过时）；
5. **反查**：从任一 Issue/Run 详情查看「依据字段指向它」的全部知识条目（证据可回溯）；
6. 按适用范围查（教训类：按角色/任务类型）。

知识是否自动注入 agent 运行上下文（token 成本与上下文污染问题）→ Q14，MVP 推荐纯检索。

### 11.4 与 bd memories 的关系【判断·给结论与理由】

【事实】workspace context〈项目经验检索〉现行明文：bd memories 用作项目级与跨项目知识库，踩坑/机制认知/经验教训必须写入 bd memories（带可检索 key）。

**结论：替代，分两步（→ Q13）。**

1. 平台知识库上线时，bd memories 既有条目**一次性汇入**为「有效」状态存量，原 key 保留为检索标签；
2. 此后新知识只写平台知识库；bd 的**任务跟踪职能不变**（bd issue/任务拆分不在替代范围，只替代其 memories 知识职能）；workspace context〈项目经验检索〉条款的修订提请 Owner 走立法流程（依赖项，不由本规格执行）。

理由：并存双写必然状态漂移（同一知识两处真值），「定期汇入」是又一个需要维护的同步器负资产；一次性迁移 + 单一事实源是唯一不产生长期维护成本的结构。风险：成员日常用 bd CLI 顺手，若平台检索/写入摩擦大，会被绕回——缓解：检索入口（§11.3）与提交入口（提案池）必须覆盖 bd memories 的全部使用场景，架构阶段提供等价的 CLI/API 读取路径，此条列入 ADR v2 核查项。

## 12. Skill 提案、评价与版本化（Owner 第 5、6 条）

Owner 原文：「把重复性高的、较长的固定化流程归纳总结成skill提案」「SKILL的执行也要有评估评价机制，对于归纳总结的skill也要有版本化管理」。

### 12.1 什么样的流程够格被提成 skill 提案【判断·可机械判定判据】

「重复性高」不可判定，够格判据全部换成机械条件，**四条同时满足**扫描器才生成 skill 提案：

1. **复现次数 ≥3**：同一流程模式在滚动 30 天窗口内被识别 ≥3 次，且每次识别附命中的历史 run/issue 证据（证据 <3 条不生成提案）。流程模式的识别口径（工具调用序列相似度）归架构定义，产品要求是「每次命中必须有证据可查」。
2. **步骤长度 ≥5**：核心步骤计数 ≥5。理由：5 步以内的流程直接写进角色提示词或 handbook 分册更合适（更短的固化手段已存在，独立 skill 是过度封装）。阈值为初始默认，Owner 可调。
3. **完成判据可陈述**：该流程的目标能写成「做完后某物处于某状态」的可判定陈述；强临场判断型任务不入围。
4. **无一次性要素**：流程不含特定 Issue 号、特定人名、一次性凭据等不可复用项（机械检查：凭据模式扫描 + 一次性要素占位符化改写，改写不了的直接拒绝生成提案）。

判据阈值（3 次 / 5 步 / 30 天窗口）是平台配置，修改留痕（→ Q15）。

### 12.2 提案到正式 skill 的流转【判断】

- 提案草稿必填：名称、适用角色与场景、流程正文（SKILL.md 形态草稿）、判据命中证据（12.1 的 ≥3 条引用）、预期收益一句话。
- Owner 在提案池采纳（打勾，交互同 §10.3，含确认步）→ 生成**平台 skill 实体**并分配给目标角色。【事实】平台 skill 实体体系已存在（创建/导入/更新/刷新/分配能力，`multica skill` 命令族；本工作空间当前登记数 0；运行时本地文件系统技能与平台 skill 并存是现状）。本单产出的 skill 落平台 skill 库，不写运行环境文件系统；平台 skill 如何被运行时加载属架构核查项。
- 拒绝 → 归档留痕。采纳即生效，不设试用态（效果评价 §12.3 持续跟踪，坏 skill 会被数据暴露，试用态的复杂度不值）；此为产品判断，Owner 可推翻。
- skill 修订与下架同走提案池（类型⑤的修订子类），Owner 采纳。

### 12.3 skill 执行效果的评价口径【判断】

两个问题、两组口径，全部复用 v1 §4 既有指标体系，不新造指标：

1. **用没用上（采纳率）**：skill 分配后，其适用场景的执行中实际按 skill 流程走动的比例。产品要求：每次 skill 被使用必须留下使用记录（run、时间、skill 版本号）；「适用场景命中」的识别口径归架构。
2. **用了好不好（效果）**：对比口径 = 同角色同任务类型，使用 skill 的执行组 vs 未使用的历史窗口组，对比指标直接继承 run 级既有指标（困惑分、返工率、一次通过率、token）。skill 化的目的是「省事且稳」，指标不必发明新的。
- 样本纪律沿用 v1 §5.2：两组各 ≥5 个样本才出方向性标签（提升/持平/劣化）；任一侧不足显示「样本不足」，禁止方向性文案。
- 效果差的 skill 不是自动下架，是**修订/下架提案的输入**——决定权在 Owner（提案权与修法权分立，同 §10.3）。

### 12.4 skill 版本化要回答的三个问题【判断】

1. **现在用的是哪个版本、谁改的、为什么**：版本台账（整体快照、只追加、copy-forward 回滚，与 prompt 版本管理同构）。
2. **改完之后效果有没有变差**：版本切换事件 + 使用组指标前后对比，样本纪律同 12.3。
3. **哪些角色在用哪个版本**：分配关系随版本可追溯。

【判断】**skill 版本管理不新造机制，是版本管理实体扩一类**（版本模型从四级 prompt 扩展为「prompt 四级 + skill」五类对象；具体存储设计归架构）。这是对 v1 §2.4「skills 资产版本管理另行立项」的显式修订依据：Owner 第 6 条已将其纳入本单，且复用同一机制后边际成本低（见 §14 冲突记录 C2）。

## 13. 增量验收标准（可机械判定，逐块单列，不与 v1 §6 合并）

### 13.1 测验机制（E1–E8）

- **E1** 题库中任一道题缺少五要素（题面/≥3 条验收条款/证据落点/适用映射/判分配置）之一时，保存被拒绝并返回缺失字段清单。
- **E2** 任一级 prompt 产生新生效版本后，系统自动创建一次测验任务，范围等于该层级映射的必考题组，测验记录含被测版本号；映射外的角色题组不被触发（范围断言）。
- **E3** 测验 run 在受控环境执行：其产生的任何 Issue/评论/产物带测验标记，且不出现在任何真实 Issue 的时间线中（标记字段非空 + 真实 Issue 流零污染断言）。
- **E4** 评分器对每题输出逐条 PASS/FAIL，每条判定附证据引用；构造无证据引用的判定输入时，系统判该判定无效。
- **E5** 注入一道已知失败的题（在题面设置必触发的错误点），测验结果正确给出该题 FAIL，且失败项与注入点一致。
- **E6** 构造新版本在某题上由基线 PASS 转 FAIL 的场景：看板该版本显示「存在回归」标签与回归题清单；从未测验的版本显示「未测验」标签。
- **E7** 题目与判分配置的修订生成新版本并留审计记录（操作者/时间/变更说明）；非 Owner 身份修订被拒绝。
- **E8** 题库首次启用时系统对当时生效版本自动建基线；此后任一回归判定的报告可点开其引用的基线成绩记录，记录含四级版本号。

### 13.2 扫描与提案池（SC1–SC7）

- **SC1** 每日扫描按配置时区在配置时刻执行；每条发布的草稿含类型/摘要/建议动作/≥1 条证据引用/批次号；构造无证据引用的草稿输入时，其被丢弃且仅在批次日志计数。
- **SC2** 同一批次重跑不产生重复草稿；D-1 窗口外的完结 run 不被本批次扫描（窗口断言）。
- **SC3** Owner 对类型①提案点采纳后：系统生成目标实体新版本草稿 + diff 预览 + 门闸校验结果；构造门闸 FAIL 的草稿时，提案转「需修订」并显示违规明细，不产生版本。
- **SC4** Owner 确认后新版本生效，且该版本审计记录含来源提案号；从版本审计可反查提案，从提案可点查立法结果（双向可达）。
- **SC5** 未采纳提案满 30 天自动转「已归档」，不删除；归档提案可检索、可恢复为草稿。
- **SC6** 成员身份可提交提案；成员身份执行采纳/确认操作被拒绝并返回权限错误。
- **SC7** 提案池对每条提案展示完整状态链（草稿→已采纳→已生效/已转化/需修订→归档）；零产出日的批次心跳记录可查。

### 13.3 知识库（K1–K6）

- **K1** 任一类型条目缺任一必填字段（§11.1 清单）时保存被拒绝并返回缺失清单；「项目认知」缺所属项目字段必拒。
- **K2** 扫描生成的知识草稿初始状态为「待确认」；检索结果中「待确认」条目带状态标签；Owner 或授权角色确认后转「有效」（确认权归属 → Q16）。
- **K3** 构造与既有「有效」条目判重命中的新条目：系统不新建、提示追加佐证去向；人工执行拆分后原条目与新条目并存且拆分动作有记录。
- **K4** 检索入口四项能力各验证一个可命中用例：关键词全文检索、按项目过滤、按类型过滤、按状态过滤。
- **K5** 从任一 Issue 详情可见「关联知识」列表，内容等于依据字段反向指向该 Issue 的全部条目（计数一致断言）。
- **K6** bd memories 汇入完成后：抽验 ≥10 条既有条目在平台知识库按关键词与原 key 均可检索命中（Q13 采纳后执行）。

### 13.4 Skill（SK1–SK6）

- **SK1** 构造仅命中 2 次复现的流程：扫描器不生成 skill 提案；构造命中 3 次且证据齐备的流程：生成提案，提案含全部必填字段与 ≥3 条证据引用。
- **SK2** 提案采纳并确认后生成平台 skill 实体并完成角色分配；分配角色的后续 run 中产生 ≥1 条该 skill 的使用记录（记录含 run/时间/版本号）。
- **SK3** 任一 skill 的修改生成新版本（整体快照、只追加），版本台账含操作者与变更说明；回滚后生成内容等于源版本的新版本，源版本保留不变。
- **SK4** 按 skill 聚合的使用次数、按版本分组的使用次数均可查询且数值一致（同一使用记录不重复计数）。
- **SK5** 使用组与未使用组各 ≥5 样本时显示方向性标签；任一侧 <5 时显示「样本不足」且页面无方向性文案（沿用 v1 §5.2 纪律）。
- **SK6** 非 Owner 身份执行 skill 版本修改/删除/下架被拒绝；成员经提案池提交 skill 修订提案成功。

## 16. 安全与合规补充（分派卡要求）

1. **内容红线**：知识条目、提案草稿、skill 正文、题目题面，一律不得包含凭据、Token、密码、验证码、私钥、未脱敏 PII。生成侧：扫描器产出过敏感模式检查，命中即脱敏或拒发（拒发计入批次日志）；人工提交侧过保存门闸（与 prompt 保存同一套凭据模式检查）。
2. **会话 jsonl 数据源**（Owner 第 7 条兜底口径的产品侧要求）：进入提案或知识条目的证据引用优先使用元数据（Issue/run ID、SHA、结论句），粘贴会话原文时必须经脱敏管道；未经脱敏的会话原文不得作为提案正文或知识条目内容落库。脱敏实现归架构，产品验收 = K 系列与 SC 系列条目中敏感模式零命中。
3. **测验隔离**：测验 run 只在受控环境执行，不得接触生产 Issue、共享数据库与真实用户数据（E3 断言）。
4. **本增量文档自检**：全文无密钥、无连接串、无内部凭据。

## 17. 风险与假设（增量）

- 【假设】平台 skill 实体支持后续追加版本维度与使用记录（§12 复用前提）；平台 skill 与运行时本地技能的加载关系待架构核查。
- 【假设】流程模式识别（工具序列相似度）的准确率足以支撑 SK1 的 ≥3 次判据；识别算法归架构，若误报率高，skill 提案会噪声化——缓解：提案必须 Owner 采纳，噪声提案被拒绝即止损，扫描器命中率本身纳入扫描批次日志观察。
- 【风险】每日扫描产出的提案噪声（低质量草稿淹没 Owner）→ 缓解：证据引用强制 + 置信标记 + 同类合并 + 30 天归档；批次日志跟踪「提案采纳率」，采纳率持续过低时是扫描规则需要调优的信号（调优规则属平台配置，Owner 可改）。
- 【风险】「Issue 不再写显式复盘」落地初期信息断档（扫描覆盖不到的隐性经验流失）→ 缓解：成员直提提案入口保留（§10.2）；过渡期双轨（扫描 + 成员自提）本身不冲突。
