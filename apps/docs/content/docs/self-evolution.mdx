Self-Evolution is the prompt-governance workbench of a workspace. Open **Self-Evolution** in the workspace sidebar to inspect the version history and quality measurements of [agent](/agents) prompts, run regression quizzes against a fixed question bank, and turn observations into improvements through legislation proposals and the knowledge mirror.

The page has eight tabs: Overview, Quality, Versions, Quiz, Skills, Legislation, Retrospective and Knowledge. It opens on Quality by default.

## Overview

The overview aggregates the core readings of the other tabs into six cards: Prompt version activity (current versions and recent changes per carrier), quality readings (per time window, with environment and vendor failures excluded), quiz conclusion (baseline vs. current comparison), proposal pool (metrics pending), knowledge mirror (registered directories and entry counts) and skill observations (count and cumulative explicit invocations).

## Quality

The Quality tab shows a run-measurement dashboard for one agent's prompt. Pick an agent with the **Subject** selector at the top (subjects are agents only for now), then adjust the statistics window with the **Window** picker (last 30 days by default).

The dashboard reads seven dimensions:

| Dimension | Meaning |
|---|---|
| D1 Injected / run cost | Median tokens of the assembled prompt injected per run; median total tokens a run consumed. |
| D2 Discipline | Median discipline score out of 100: a run starts at 100 and loses points for each mechanically checkable clause it broke. |
| D3 Rule perplexity | An ambiguity score for the assembled prompt, judged per runtime profile (member run / leader task run), never merged or averaged. |
| D4 Turn failure rate | Share of tool results the agent received as errors. |
| D5 Retries | Share of runs that needed more than one attempt. |
| D6 Prompt-attributed failures | Failures whose cause points at the prompt; environment and provider failures are excluded. |
| D7 First-pass rate | Share of reviewed issues accepted without rework. |

**All versions in window** splits the readings by prompt version: select two versions on the timeline to compare them dimension by dimension. **Manage versions** jumps to the Versions tab.

## Versions

The Versions tab is the entry to the prompt version lifecycle. One rule governs it: **every effective change appends a version; history is never rewritten**.

The version line covers six prompt carriers: workspace, project, squad, agent, autopilot and skill. The page offers no content editing: a version is created by taking a snapshot of the carrier's currently effective configuration; to change a carrier's content, use the carrier's own management entry.

Pick the **carrier type** at the top first, then the **carrier** under it. The workspace type needs no second pick — it is this workspace itself. Without a carrier the page only shows a placeholder.

### Taking a snapshot

1. After picking a carrier type and a carrier, click **Snapshot** at the top right and confirm.
2. The carrier's currently effective configuration is recorded as a new version (source badge "Snapshot"); the carrier's own content is not changed.
3. Snapshots may be repeated: unchanged content can be snapshotted again, and every snapshot appends a new version.
4. A snapshot's change note defaults to a fixed text ("snapshot of the current effective configuration").

<Callout type="warning">
Snapshots pass the same gates as every version write: the snapshot is refused when the carrier's effective content is empty or exceeds 200 KB (400), and refused when it appears to contain credentials (422) — with the matched rules, line numbers and masked samples. Remove the flagged content on the carrier's own management entry first, then take the snapshot again.
</Callout>

### Activating and rolling back

The version list is ordered newest first. Each row carries a source badge (Baseline / Edit / Rollback / Auto snapshot / Snapshot), the change note, the creation date, a content fingerprint prefix and a quality badge; the newest row also shows a **Latest** badge.

Activating any historical version (**Activate**) performs a rollback: its content is copied forward as a new latest version and takes effect immediately, while the old rows stay untouched. Versions created by a rollback show "from vN". You can later activate an even older version to undo the switch — history only grows, and every switch leaves a complete trail.

### Comparing any two versions

Click two version chips to open a content diff of the two. Clicking a third chip replaces the older selection; **Clear selection** exits the comparison.

### Quality binding

Quality evaluation binds each run to the prompt version it claimed. The badge on each version row shows how many runs that version served, so you can see directly which version preceded each quality change.

### Write access

Reading versions is open to every member; **Snapshot** and **Activate** are workspace-owner only (admins are not included). Non-owners see no write controls.

## Quiz

The Quiz tab replays one fixed question bank against every prompt version and produces a regression reading: with one version as the baseline, it compares the reading distributions of the current version (median, IQR) and issues a verdict — improved / steady / regressed / no reading.

- A reading is a distribution, not a single score; no comparison is shown until a group has enough samples.
- A quiz never blocks a prompt version from being published. It records how quality changed.
- The **Question bank** panel manages the fixed questions: add, edit and retire them. Editing a body starts a new revision; readings are only compared within the same wording, runtime and model.
- A question must be self-contained and must not name any production entity (issue key, id, link); the server refuses such bodies.
- Bank writes are workspace-owner only. The answer key and grading points are owner-only and never sent to the run being measured.

## Skills

The Skills tab shows the version history and observed usage of [skills](/skills): which agents they are assigned to, explicit invocation counts, median token cost per version, and version measurements — median run tokens, retried runs and first-pass rate, comparing a use group against a control group.

Differences across versions are observational and do not prove that the skill caused a change; a delta appears only when both sides have at least five valid run samples.

Restoring a historical version is append-only too: an owner clicks **Restore version** and the content becomes a new version; assignments remain unchanged.

## Legislation

The Legislation tab manages clause-level Prompt improvement drafts for the four Prompt carriers (workspace, project, squad, agent). Each proposal binds a target section and a change kind (add clause / remove clause), carries the final clause text and evidence anchors (issue number + quote); submitting for approval requires completing the five content-gate answers: layer assignment, retention rationale, cost statement, conflict ruling and duplicate check.

Proposals flow draft → pending owner → approved → enacted. Gate-failed and rejected proposals stay on record and can be reworked for resubmission or restored to draft. Source labels distinguish manual drafts, daily-retrospective automation and merges.

Every member can draft, edit and submit their own proposals; approving (including batch approval, up to 20 per batch), rejecting, restoring to draft and enacting are workspace-owner only. Approval requires previewing the full-carrier diff in the sandbox and confirming it explicitly; enacting reruns the legislation gate and writes the effective configuration only on a clean pass.

## Retrospective

The Retrospective tab is a built-in scheduler: it reads the real execution content of completed issues inside the lookback window, distills Prompt improvement drafts and drops them into legislation proposals in batches, without ever posting issue comments.

The config area offers a scheduled-run toggle, an "also scan in_review issues" option and the lookback window in days; saving applies the config, and "Run now" triggers a manual pass. The runs list shows each run's status (succeeded / failed / running), window, scanned / analyzed / created / merged / duplicate-skipped counts and errors.

Without an LLM configured, a run records a failed entry naming the missing configuration. Viewing the config and runs is open to every member; changing the config and running now are workspace-owner only.

## Knowledge

The Knowledge tab mirrors bd memories directories read-only: the connected daemon auto-discovers project-local bd memories, and local directories can be added manually. After registering a directory you can run scans (showing added / updated / removed counts) and search the entry mirror by key or content.

The mirror itself is read-only: the only write path is an owner adopting a pending entry, which transfers the content into the knowledge hub. Registering, scanning, unregistering and adopting are workspace-owner only.
